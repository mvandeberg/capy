= Buffer Types
:page-mode: explanation

This section introduces Capy's fundamental buffer types: cpp:const_buffer[] and cpp:mutable_buffer[].

== Buffers Are Handles

A cpp:const_buffer[] or cpp:mutable_buffer[] is a *handle*: a non-owning `(pointer, size)` view of memory it does not own. Constructing one copies no bytes, and destroying one frees nothing.

This splits lifetime responsibility cleanly:

* *You own the bytes.* The memory a buffer refers to—a stack array, a `std::string`, a slab from your allocator—is yours to keep alive. It must remain valid for the entire duration of any operation you hand the buffer to. That includes the suspension points of a `co_await`-ed I/O operation.
* *The library owns the handles.* Capy creates and manages buffer handles and handle-sequences on your behalf. Those handles are the buffers a dynamic buffer exposes through `prepare`/`data` and the sub-range a cpp:buffer_slice[] produces. They are also the descriptors a type-erased stream passes to the OS. Each such handle is valid only for the window its API documents, typically until the next call that mutates the owner.

The library never copies or takes ownership of your bytes through a buffer; it only moves handles. This split explains every buffer-lifetime rule in this chapter.

== Why `void*`, Not `std::byte`?

`std::byte` imposes a semantic opinion. It says "this is raw bytes"—but that is itself an opinion about the data's nature.

POSIX uses `void*` for buffers. This expresses semantic neutrality: "I move memory without opining on what it contains." The OS doesn't care if the bytes represent text, integers, or compressed data—it moves them.

Two concrete forces favor `void*` specifically over `std::span<std::byte>`:

* *Platform types already use it.* The OS structures Capy maps onto—`iovec`'s `iov_base`, `WSABUF`'s `buf`—are `void*`/`char*`, so the pointer field never needs reinterpreting. Only `iovec` matches Capy's full struct layout; `WSABUF`'s field order and width differ, as the Layout Compatibility section below explains.
* *Callers supply many element types.* User data arrives as `char[]`, `unsigned char[]`, `std::byte[]`, `std::string`, and more. A single neutral pointer erases all of them to one representation. `std::span<std::byte>` would force every caller to reinterpret their bytes first, and `std::span<void>` is ill-formed—{cpp} cannot express a type-agnostic buffer with `span`.

Capy provides cpp:const_buffer[] and cpp:mutable_buffer[] as semantically neutral buffer types with known layout.

cpp:make_buffer[] accepts any sized, contiguous range of trivially-copyable
elements—including `std::span` and `boost::span`—in addition to the
sources shown above.

The returned buffer type depends on the element constness of the range:

* Ranges of mutable elements → cpp:mutable_buffer[]
* Ranges of const elements, `string_view`, string literals → cpp:const_buffer[]

The buffer's size, in bytes, is `count * sizeof(element)`.

== Layout Compatibility

cpp:const_buffer[] and cpp:mutable_buffer[] place the pointer first and the size second:

* POSIX: `struct iovec { void* iov_base; size_t iov_len; }` — same order, same widths. An array of buffers converts to `iovec` with a direct reinterpret_cast.
* Windows: `struct WSABUF { ULONG len; CHAR* buf; }` — reversed order, and a 32-bit length instead of `size_t`. Capy copies descriptors into a `WSABUF` array instead of casting; see xref:5.buffers/5d.system-io.adoc[System I/O Integration].
